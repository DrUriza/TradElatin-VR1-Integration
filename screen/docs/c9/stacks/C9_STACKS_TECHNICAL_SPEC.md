# C9 Stacks/sBTC Technical Specification

## Document status

**Status: Planned / In Development — Pre-Implementation Specification.**

This document defines the proposed Screen-side boundary and observable surface
for C9 on Stacks/sBTC. It is documentation only. It does not implement C9, add
an HMI route, add a JSON contract, contact a Stacks provider, or add an endpoint
to the current application.

The current Screen repository represents C1-C8. C1-C8 are implemented and
validated primarily through emulator, synthetic-data, and replay workflows.
No Stacks adapter exists today. No operational Stacks data pipeline exists
today. No Stacks C9 HMI exists today. The adapter, normalization, versioned C9
contracts, and C9 HMI are proposed grant deliverables whose implementation
begins in Milestone 1. This specification does not state or imply grant approval.

## Ownership and architectural boundary

The proposed end-to-end pipeline is frozen as:

```text
Stacks/sBTC
→ Adapter
→ Normalization
→ Versioned C9 Contracts
→ Financial Observables
→ HMI
```

Screen belongs at the final boundary. It must consume Processing-generated,
versioned contracts and render their contents. The HMI itself does not contact
providers, query contracts, index chain events, normalize source payloads, or
derive live-provider status. Live-provider status is generated by Processing
and rendered by Screen.

**C9 owns the Stacks/sBTC data, while C1–C8 can consume C9 observables for cross-family contextual analysis.**

Cross-family consumption does not transfer data ownership and must not change
the meaning of an established C1-C8 metric. C9 remains the canonical owner of
Stacks/sBTC source lineage, normalization, quality, and operational state.

## Committed C9 observables

Only the following three observable groups are committed by this
pre-implementation specification.

### C9.1 — sBTC Supply & Peg State

- sBTC total supply
- supply change / net issuance
- mint/burn-related supply activity
- peg/bridge-cap context where supported by the selected public sources
- derived reconciliation metrics only when technically supported by the source data

The future contract must preserve source provenance and distinguish direct
source values from derived reconciliation metrics.

### C9.2 — sBTC Bridge Flow

- BTC→sBTC deposits
- sBTC→BTC withdrawals
- gross deposit volume
- gross withdrawal volume
- net bridge flow
- operation counts
- operation-size distributions where supported

Bridge direction, amount units, timestamps, and operation identity must be
normalized before the data reaches Screen.

### C9.3 — sBTC Bridge Operational State

- pending / accepted / confirmed / failed operations
- deposit RBF state where applicable
- pending value
- operation age / settlement timing where derivable
- fulfillment BTC fees where available
- withdrawal capacity / limits
- chain-state and bridge operational context

Operational state must be reported as observation and provenance, not converted
by Screen into a prediction or trading signal.

## Proposed source families

The following are proposed source families for future implementation and must
be validated during grant work before they are treated as operational:

- official sBTC contracts such as `sbtc-token` and `sbtc-registry`
- Emily public API
- Stacks node/read-only contract interfaces
- Hiro / Stacks indexed APIs
- protocol-specific contracts/events for future transversal observables

Listing a proposed source does not assert coverage, stability, semantic
compatibility, or present integration.

## Proposed transversal source surface

This section defines future extensibility and contextual use by C1-C8. It is
separate from the three committed C9 observables and is not implemented.

### C1 Prices

- sBTC market price / BTC deviation when a reliable market source exists
- DEX/pool execution context

These items are proposed only; they are not present in the current C1 HMI.

### C2 CVD & Order Flow

- sBTC transfers
- DEX swaps / signed flow where semantics allow it

Simple transfers must not be labeled CVD. Buyer, seller, or aggressor semantics
may be used only when they can be established correctly from the validated
market mechanism and source data.

### C3 Open Interest & Funding

- Stacks lending/borrowing/utilization/rates as contextual data

Lending metrics must not be labeled Open Interest or Funding.

### C4 ETF & Exchange Flows

- BTC→sBTC deposits
- sBTC→BTC withdrawals
- gross and net bridge flows

These are bridge observables owned by C9 and may be consumed by C4 only as
cross-family context.

### C5 On-Chain & Miners

- sBTC supply
- mint/burn
- transfers
- holders
- bridge completion
- signer/registry state

These observables do not replace the existing Bitcoin miner metrics in C5.

### C6 Volatility

- bridge stress
- pending/failed/RBF activity
- peg-related changes where measurable
- fees
- network/bridge operational conditions

Any future composite or derived stress measure must retain its definition,
inputs, source support, and quality metadata.

### C7 Liquidations

- future Stacks DeFi/lending liquidation events when a specific protocol and source are validated

Stacks DeFi/lending liquidation events must remain distinct from derivatives
liquidations.

### C8 Liquidity Microstructure

- DEX/AMM pool state
- reserves
- swaps
- slippage
- price impact

AMM liquidity must not be presented as order-book depth.

## Screen pre-implementation constraints

Until grant implementation begins, this repository must not:

- add a C9 route or navigation item to the HMI
- add a C9 JSON contract or fixture
- add Stacks/sBTC providers or adapter code
- invent or display sample Stacks data as operational data
- claim operational Stacks support
- claim grant approval

Future Screen work must start from a versioned Processing contract and preserve
the established rule that Screen renders but does not acquire or normalize
provider data.
